GIKAL Wortmeister - WASM Version

About the Project

GIKAL Wortmeister is a web based application that supports the German vocabulary memorization process with spaced repetition and level based progression. The project was prepared for the students of Göztepe İhsan Kurşunoğlu Anatolian High School.

It consists of three main components:

  1. Rust based HTTP server
  2. Rust WebAssembly core
  3. HTML/CSS/JS frontend

Although the infrastructure for this has not been fully prepared yet, once ready users will be able to register and log in to save their progress on the server, continue as a guest and keep their data in the browser, or manually create and study their own word lists.

Architecture

The user sends input from their browser, the input is carried to the Rust Axum server and written to users.json. Afterwards, it is transferred to the WebAssembly module together with static files like index.html, styles.css, and WASM. Checks are performed using the word catalog embedded via include_dir! and words normalized during the process.

Layer Responsibilities

Server (main.rs)

  • User account management
  • Session authentication with UUID token
  • Storing progress and statistics data in a JSON file
  • Serving static frontend files with tower_http::services::ServeDir

WASM Core (lib.rs) (The main event on the Rust side happens here)

  • Converts all JSON word files under words/ into a catalog at compile time
  • Provides functions to be called from JavaScript:
    • get_categories, get_sets, get_words, get_category_name
    • check_answer
  • Answer checking steps:
    1. Raw and normalized matching checks
    2. German articles are cleaned up (It seemed unnecessary at first but I decided to add it later for assurance)
    3. Multiple alternative support
    4. Ignoring parenthetical explanations
    5. Similarity scoring with normalized_levenshtein (85% correct, 65% close threshold).
  • After each answer result, the word level is updated between 1 and 5

Frontend (classic CSS, HTML, JS trio)

  • Screen transitions (auth, menu, category, set, game, end, addWords...)
  • Session and guest progress via sessionStorage / localStorage
  • Saves progress to the server after authentication (/api/auth/save)
  • Synchronized communication with the WASM module
  • Responsive design, custom CSS animations (confetti on the end screen, streak explosion, box shaking on incorrect answers).

Server API Reference

All requests use the POST method and require Content-Type: application/json

WASM Function Reference

All functions exported via wasm-bindgen return a JSON string

Answer Checking Algorithm

The check_answer function responsible for this task performs the following checks in order:

  1. Direct match: The user's answer is compared to the correct answer using trim().to_lowercase()
  2. Spaceless match: All spaces are removed and the comparison is repeated
  3. NFKD normalization: Both texts are decomposed using Unicode NFKD, then German/Turkish special characters are converted to their ASCII equivalents (ä→ae, ß→ss, ş→s etc.) The normalized texts are compared
  4. Article stripping: German definite and indefinite articles are removed using strip_article(), the remaining part is compared both raw and normalized
  5. Alternative translations: If the correct answer contains the / character, normalized and similarity checks are performed for each alternative. If Similarity ≥ 0.85, it is considered correct (I chose the classic Turkish Education System method XD)
  6. Parenthetical explanations: If there is a ( in the correct answer, the part before the parentheses is checked using the same methods
  7. Levenshtein similarity: If none of the above match, similarity is calculated using normalized_levenshtein. ≥ 0.85 is considered correct, ≥ 0.65 is considered close

Level update:

  • Correct: If old_level is less than 5, it increases by 1.
  • Incorrect: If old_level is greater than 1, it decreases by 1.
  • Thus the new level always remains between 1 and 5.

Progress and Statistics Data Structure

progress

Keys are the combination of category and set ID (e.g. "hazirlik_1"). Each entry: 

{
  "category": "Hazırlık",
  "setName": "Hazırlık / 1. Ünite",
  "masteredCount": 42,
  "totalCount": 50,
  "updatedAt": "2025-01-01T12:00:00.000Z",
  "words": [
    { "foreign": "der Hund", "translation": "köpek", "level": 5 },
    ...
  ]
}

stats Object

{
  "bestStreak": 15,
  "totalCorrect": 120,
  "totalAnswered": 145
}

For logged in users, this data is saved both to the server (/api/auth/save) and to localStorage as a backup. For guests, since there is no user field to save to, only localStorage is used

Build and Run

I don't know who would compile this but I thought I'd write it down

1. Build the WASM module

wasm-pack build --target web --out-dir static/pkg

This command creates the necessary .wasm and .js bindings under static/pkg/

2. Build the server

cargo build --release --bin wortmeister-server

3. Start the server

USERS_FILE=users.json STATIC_DIR=../static PORT=9090 ./target/release/wortmeister-server

Environment variables:

  • USERS_FILE: User database file (users.json)
  • STATIC_DIR: Directory containing static files (frontend etc.) (../static)
  • PORT: Server port (default: 9090)

4. Access

Access is provided by entering the port in the browser

Frontend Screens

  • authScreen: Registration, login, and continue as guest options
  • menuScreen: Main menu, set selection, manual word addition, continue, logout...
  • categoryScreen: Grade, category selection
  • setScreen: Unit set selection
  • gameScreen: Word card, level indicator, answer input, feedback, progress bar...
  • endScreen: Congratulations screen and confetti when all words are completed
  • addWordsScreen: User creating their own word list

Security Notes (Because I want to be a Hardware Security Specialist in the future)

  • Passwords are hashed using SHA256(username + ":" + password). Since no salt is used, bcrypt or argon2 is recommended in production
  • Session tokens are UUIDs and stored in plain text. I think it is sufficient for an educational application that does not contain sensitive data
  • I made an effort to configure CORS to allow all sources (CorsLayer::permissive()). It is only suitable for use on an internal network
